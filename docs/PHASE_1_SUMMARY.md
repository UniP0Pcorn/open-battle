# 阶段一收尾：规则引擎、编成和数据导入基础

## 阶段结果

本阶段把项目从移动沙盒推进到可运行的本地数字对战原型：规则逻辑集中在 `rules/`，Godot 场景负责输入、显示和命令日志，JSON profile 与军表负责数据驱动。桌面流程已覆盖移动、射击、冲锋、近战、目标控制、战斗震慑、指挥点、存档和确定性回放。

最终回归命令：

```powershell
godot --headless --path . --script tests/run_tests.gd
```

最后一次验证结果：**308 项检查，0 失败**。

## 已交付能力

- 版本化规则集目录：注册 10E/11E，profile 和军表校验版本与阵营一致性。
- 军表编辑：单位条目、数量、分数上限、阵营设置、JSON 导入/导出和回滚式校验。
- 对战流程：移动额度与队形连续性、前进、撤退、地形阻挡、视线/曲射、射击、手枪接战限制、掩体、普通/无敌豁免、冲锋、近战、危险武器、一次性武器、爆炸、毁灭伤害、目标控制和战斗震慑。
- 状态一致性：`TurnState`、指挥点、模型独立移动/属性、损伤状态、命令日志和本机存档同步。
- 回放：移动、前进、撤退、冲锋、回合、战斗震慑、射击/近战伤害和危险武器事件可验证重放。
- 兵牌工具链：PDF 候选提取、草稿生成、复核表导出、严格晋升、批量晋升和 profile 目录重建。
- 数据索引：30 个来源记录、30 个待复核 profile、31 个目录索引条目；候选工作区当前有 643 个草稿，261 条基础结构字段完整候选，其中 179 条已通过当前审核表的字段与武器标签筛选，仍需人工确认底座、阵营与编成字段。

643 条是从来源 PDF 自动切出的候选行，包含重复单位、页眉误识别、单模型/多模型分值混排和能力文本混入，不能直接当作 643 张可用兵牌。当前复核表的主要原因是：89 条仍缺少可确认的分值，246 条含尚未接入执行器的武器关键词，239 条武器伤害不是固定数值，204 条攻击次数不是固定数值，23 条没有可靠武器行，另有 24 条移动值和 18 条目标控制值需要人工确认。新增的分数解析会识别“单位构成 一台……250分”和“3+个 280分”等短格式，并优先采用明确的单位构成价格；“反步兵/反载具/反飞行/反巨兽”以及繁体武器关键词会映射到已有规则。近战武器行现在也会进入草稿，复合关键词会拆分处理；因此当前有 179 条可直接进入“待确认底座/阵营”的候选。它们可以同时命中多个原因，所以这些数字不能相加得到 643；复核目标是把候选压缩成可追溯、可验证的正式 profile。

## 数据边界

仓库不包含用户提供的 PDF 原件，也不复制长篇官方规则文本、美术或徽记。待复核数据只保留结构化属性、来源文件名和页码；正式 profile 只有在阵营、底座尺寸、连结距离、武器选项和能力字段确认后才能进入可用目录。原型 profile 的数值仍应视为测试配置，不能宣称已核验为官方版本。

## 当前限制与下一阶段

- 当前仍是本地 Godot 原型，没有联机房间、账号权限、服务器权威状态或 3D 表现。
- 规则模块覆盖了主要流程，但完整版本规则、任务、阵营能力、编队限制和全部兵牌仍需按来源逐条复核并导入。
- 继续工作时优先顺序：复核并晋升首批 profile，补齐任务/阵营规则边界，建立服务器权威命令协议，再实现联机同步和发布构建。
